# MVP 总体架构与统一底座设计

> 本文是从战略文档（1-19 号）到 MVP 开发的总体设计。回答"系统整体长什么样、各模块如何配合、底座如何承载未来扩展"。
>
> 适用读者：CTO / 架构师 / 产品总监 / 各产品 PM。
>
> **设计原则**：
> 1. **统一底座，模块解耦**：6 大 SaaS + 数据中台 + 集采/金融生态共用一套用户/权限/计费/事件/审计中台
> 2. **场景驱动**：所有架构要覆盖 1-19 号文档梳理的全部场景（详见末尾"场景覆盖矩阵"）
> 3. **未来兼容**：MVP 不上线的功能（如金融/集采/数据指数 To B 售卖）必须在底座层预留好扩展点
> 4. **数据先行**：数据中台与各 SaaS 同期设计、同期上线（不能等业务跑起来再补）

## 二、6 大统一底座设计

### 2.1 底座 ①：用户与组织中台

#### 2.1.1 业务模型

```
租户 Tenant（一家钢贸企业）
  └─ 组织节点 OrgNode（多公司/多分支机构，树形）
        └─ 部门 Department
              └─ 用户 User（员工 / 老板）
                    └─ 角色 Role（多角色支持）
                          └─ 权限 Permission

外部用户（不属于任何租户）：
  - 散客买家（来自工地、加工厂的采购员）
  - 司机（物流 SaaS 用）
  - 第三方机构（金融/钢厂/政府，未来开通）
```

#### 2.1.2 核心字段（关键字段，详见 34 号开发文档完整建模）

| 实体 | 关键字段 |
|---|---|
| Tenant | id / name / usc_code / size_tier(小/中/大) / status / subscription_plan / created_at |
| OrgNode | id / tenant_id / parent_id / name / type(总部/分公司/仓库) / level |
| User | id / tenant_id / org_node_id / name / mobile / wechat_unionid / role_set / status |
| Role | id / name / permissions[] / scope(tenant/org/global) |
| ExternalUser | id / type(buyer/driver/3rd_party) / mobile / verified_at |

#### 2.1.3 关键设计点

| 点 | 说明 |
|---|---|
| **多组织** | 集团客户必备（中大型钢贸有多公司多账套） |
| **多账号** | 一个手机号可关联多个企业（业务员可能服务多家） |
| **微信 unionid** | 微信生态多端打通（公众号/视频号/小程序/企微） |
| **角色矩阵** | 老板 / 业务员 / 财务 / 仓管 / 司机 / 客户成功 / 客服 / 管理员 8 种角色 |
| **外部用户** | 接收对账单/合同的客户、司机、未来金融对手方 |
| **租户切换** | 一个用户登录后可在多租户间切换（多公司服务时） |

#### 2.1.4 关键场景覆盖

- ✅ 老板手机驾驶舱（02 号场景 1）：多角色权限隔离
- ✅ 业务员手机报价（02 号场景 1）：业务员角色 + 报价审批
- ✅ 仓管扫码（02 号场景 2）：仓管角色 + 仓位权限
- ✅ 财务对账（02 号场景 3）：财务角色 + 多账套
- ✅ 司机签收（02 号场景 2）：外部用户角色
- ✅ 集团多基地（03 号大型场景）：多组织树
- ✅ 业务员离职数据沉淀（03 号中型场景）：账号归属公司而非个人微信

### 2.2 底座 ②：权限中台

#### 2.2.1 RBAC + ABAC 混合模型

```
RBAC（基于角色的访问控制）：
  - 用户 → 角色 → 权限集
  - 适合：常规功能权限（看/编辑/删除）

ABAC（基于属性的访问控制）：
  - 规则：if user.org_node == data.org_node and user.role.has('view_finance')
  - 适合：数据范围权限（业务员只能看自己客户）

资源-操作-条件 三元组：
  resource: contract/customer/inventory/quote/...
  action: read/write/delete/approve/share
  condition: 表达式（org_scope / data_owner / time_window / ...）
```

#### 2.2.2 权限模板预设

| 角色 | 可看 | 可编辑 | 可审批 |
|---|---|---|---|
| 老板 | 全公司所有数据 | 关键配置 | 报价/合同/集采 |
| 业务员 | 自己客户的合同/订单/报价 | 报价/订单 | — |
| 财务 | 全公司财务/对账/票据 | 对账单/票据 | 付款 |
| 仓管 | 本仓库所有库存/出入库 | 出入库扫码 | — |
| 客服 | 自己负责客户的全数据 | 客户档案 | — |
| 司机 | 自己接单的运输信息 | 签收回执 | — |

#### 2.2.3 数据范围隔离

```
租户隔离（Hard）：
  - 不同租户的数据物理隔离（数据库列 tenant_id 强校验）
  - 任何 SQL 必须带 WHERE tenant_id = ?
  - 通过 ORM 中间件或数据库代理层强制

组织隔离（Soft）：
  - 同租户内按组织节点过滤
  - 配置项：用户可见所有 / 仅本组织 / 仅本组织及子节点

数据所有者隔离（Soft）：
  - 业务员只看自己的客户（客户与业务员关联）
  - 老板可全看
```

#### 2.2.4 关键场景覆盖

- ✅ 业务员私单飞单防控（02 号场景 4 / 03 号中型场景 2）：业务员行为风控规则 + 报价审批触发
- ✅ 客户主权机制（11 号文档）：买家与卖家首单成交后 6 个月主权 → 权限规则
- ✅ 4 级资源可见度（11 号文档）：默认 L0 私有，升级要"二次确认"

### 2.3 底座 ③：主数据中台（关键）

> 这是钢贸数字化的灵魂。错了重做成本极高。

#### 2.3.1 核心主数据

```
1. 钢材主数据 MaterialMaster
   - sku_id（唯一编码）
   - category（板/管/型/线/特钢/...）
   - sub_category（螺纹钢/盘螺/线材/中板/带钢/H 型钢/...）
   - mill（钢厂：沙钢/中天/河钢/宝武/南钢/...）
   - grade（牌号：HRB400E/Q235B/SS400/...）
   - spec（规格：Φ16/Φ20/12mm/1500×6000/...）
   - theoretical_weight_per_unit（理论重量公式）
   - default_unit（吨/支/捆/件）
   - status

2. 客户主数据 CustomerMaster
   - id / tenant_id
   - usc_code（统一社会信用代码）
   - name / aliases[] / parent_id（关联企业）
   - type（终端工地/加工厂/小钢厂/批发商/调货商/零售...）
   - region
   - main_skus[]（主营品类）
   - credit_limit / payment_score / risk_level
   - sales_owner_id（业务员归属）
   - first_dealing_at（首次成交，用于"客户主权"判断）
   - main_supplier_id（卖家主权方）

3. 仓库主数据 WarehouseMaster
   - id / tenant_id
   - name / type（自营/社会/前置/钢厂）
   - address / gps
   - capacity
   - location_tree（库区→垛位→捆位）

4. 钢厂主数据 MillMaster
   - id / name / usc_code
   - region / specialty_skus[]
   - agency_terms（年度协议）

5. 价格指数主数据 PriceIndexMaster
   - sku_id / region / date
   - source（钢联/Mysteel/自有平台真实成交）
   - price / volume

6. 合同模板主数据 ContractTemplateMaster
   - 钢厂代理 / 现货 / 调货 / 加工 / 集采 等模板
```

#### 2.3.2 钢材主数据的难点解决

| 难点 | 解决方案 |
|---|---|
| **规格组合爆炸** | sku 编码采用"分类+钢厂+牌号+规格"组合主键，不预生成笛卡尔积 |
| **理论重量计算** | 提供公式库（如螺纹 Φd 的理重 = 6.165 × 10⁻³ × d²），系统自动算 |
| **理计 vs 过磅** | 出库单字段保留两值，按合同计量方式（理计/过磅/取小/取大）结算 |
| **同义词映射** | "螺纹"="HRB400E"="带肋钢筋"建立同义词库 |
| **历史数据迁移** | 提供"钢材主数据导入向导"+ 智能匹配 |

#### 2.3.3 客户主权机制实现

```
当业务员发起报价 / 客户首次下单时：
  1. 检查 CustomerMaster.main_supplier_id 是否为空
  2. 若空 → 设置当前 tenant 为 main_supplier，main_supplier_until = now() + 6个月
  3. 若非空 → 检查是否在主权期内
     - 在主权期内：仅 main_supplier 可主动联系（其他卖家被屏蔽）
     - 主权期外：解封
  4. 客户可在 H5 主动选"换卖家"（不是默认行为）
  5. 任何卖家通过平台数据撬客 → 触发风控告警 → 永久封禁金融业务

字段：
  CustomerMaster.main_supplier_id
  CustomerMaster.main_supplier_until
  CustomerMaster.client_choice_unbind_at（客户主动换卖家时间）
```

#### 2.3.4 4 级资源可见度

```
sku_id × tenant 级别有可见度配置：
  ResourceVisibility
    - tenant_id（卖家）
    - sku_id
    - level: L0 私有 / L1 仅圈内 / L2 模糊公开 / L3 精确公开
    - target_circle_id（L1 用）
    - upgraded_at

升级激励（业务规则）：
  L0→L1: 加 50 平台积分
  L1→L2: 加 200 积分 + 担保费 8 折
  L2→L3: 流量加权 + 200 积分

升级前必须二次确认弹窗。
```

### 2.4 底座 ④：事件总线（系统神经中枢）

#### 2.4.1 设计原则

所有跨模块通信走事件，**不走点对点 RPC**。这样：
- 模块间解耦，未来可独立部署
- 数据中台天然能消费所有事件
- 风控/审计/增长分析统一订阅
- 失败可重试

#### 2.4.2 关键事件目录

```
P3 扫码出库相关：
  - DeliveryOrderCreated
  - DeliveryItemScanned
  - WeighingCompleted
  - QualityCertGenerated
  - DriverSigned
  - DeliveryCompleted
  - DeliveryAnomalyDetected

P2 电子对账单相关：
  - StatementGenerated
  - StatementSent
  - StatementViewedByClient
  - StatementConfirmed
  - StatementDisputed
  - ShareLinkVisitedByNonRegistered（核心病毒事件）
  - NewUserRegisteredViaStatement

P4 AI 报价相关：
  - QuoteRequested
  - QuoteGenerated
  - QuoteApprovedByOwner
  - QuoteSentToClient
  - QuoteAcceptedByClient
  - QuoteAnomalyDetected（业务员行为风控）

P5 资金大盘相关：
  - PaymentReceived
  - PaymentMade
  - NoteReceived（承兑票收到）
  - NoteEndorsed（背书）
  - NoteDiscounted（贴现）

P6 社区：
  - PostPublished
  - PostFlagged
  - InquiryPosted

跨模块汇总：
  - InventoryChanged（出库/入库/盘点都触发）
  - ContractSigned
  - CustomerProfileUpdated
  - SupplierAgencyTaskUpdated
```

#### 2.4.3 数据中台订阅模型

```
EventBus → 数据中台.原始层（保留所有事件，按 24h+ 落湖）
        ↓
        ├─ 实时计算引擎（钢价/库存/资金/风险）
        ├─ 批量计算引擎（指数/画像/报告）
        └─ 内部数据 API（喂给 6 大 SaaS）
```

详见 27 号文档。

### 2.5 底座 ⑤：计费中台

#### 2.5.1 计费模型

```
SubscriptionPlan
  - id / name / annual_price
  - features[]（启用的功能列表）
  - quota[]（限量列表，如对账单 100 张/月）

Subscription
  - tenant_id / plan_id / start_at / end_at
  - status（active/expired/grace_period）
  - auto_renew

UsageMetric（按量计费用）
  - tenant_id / metric_name / period
  - quota / used / overage
  - 例：扫码出库 metric_name='delivery_count'

Invoice / Payment
  - tenant_id / amount / period
  - status / payment_method / paid_at

加值服务（未来 M7+）：
  - 担保费 / 保理分润 / 集采返点 → ValueAddedRevenue
  - 与 Subscription 解耦
```

#### 2.5.2 套餐设计（与 15 号文档对齐）

| 套餐 | 年费 | 包含 |
|---|---|---|
| 基础版（免费） | 0 | 钢价行情（基础）/ 对账单（10 张/月）/ 社区 |
| 业务版 | 4,980 | + AI 报价 100 次/月 + 扫码出库 500 单/月 |
| 企业版 | 19,800 | + 全 6 SaaS 不限量 + 资金大盘 + 电子合同 + 深度行情 |
| 集团版 | 88,000+ | + 多组织 + API + 数据指数 + 专属客服 |

#### 2.5.3 计费关键场景

- ✅ 免费版用户超 10 张对账单 → 触发付费引导（不强制升级，引导下次升级）
- ✅ 业务版用户报价超 100 次 → 临时弹窗 + 历史可查 + 可购买"次包"
- ✅ 企业版自动续费提前 30 天提醒
- ✅ 集团版按用户数浮动 + 实施费

### 2.6 底座 ⑥：增长分析中台

#### 2.6.1 核心指标

```
病毒系数 K
  K = 邀请数 × 转化率
  目标：K > 1（自然增长）

激活漏斗
  注册 → 完成新手任务 → 首次发对账单 → 首次扫码出库 → 首次报价

留存
  D1 / D7 / D30 留存
  W1-W4 习惯期监控
  M1-M3 召回机制

转化
  免费 → 付费率
  付费 → 续约率
  续约 → 加购率
```

#### 2.6.2 关键事件埋点（数据驱动决策）

```
所有页面访问、所有按钮点击都埋点。
关键事件：
  - 注册（来源：自然 / 病毒 / 推广）
  - 套餐升级
  - 套餐降级 / 流失
  - 关键功能使用（每个 SaaS 至少 5 个关键事件）
  - 病毒分享 / 接收方扫码 / 接收方注册
  - 30 天习惯期：每日打开次数
```

#### 2.6.3 看板与告警

```
首页运营看板（CCO/COO/产品总监看）：
  - 实时 DAU / 注册数 / 付费数
  - 病毒漏斗（发→看→注册转化率）
  - 各 SaaS 使用 Top
  - 客户成功告警（流失风险）

老板看板（CEO 看）：
  - 当月 ARR
  - 付费客户数 / NDR
  - 现金流
  - 关键风险告警

A/B 实验框架：
  - 病毒位文案 / 引导文案 / 注册流 都可配置 A/B
```

### 3.3 数据存储分层

| 层 | 用途 | 选型方向（M1-M3 MVP 规模） |
|---|---|---|
| 业务库（OLTP） | 各服务持久化数据 | 关系数据库（云托管） |

### 3.4 安全架构（MVP 必须做到）

## 五、关键设计原则与约束（必读）

### 5.1 隐私优先（与 09/11 号文档对齐）

- 默认 L0 私有（库存/价格/客户）
- 升级到 L1/L2/L3 必须二次确认
- 每个隐私开关在 UI 中明示"我们看不到你的数据"
- 数据贡献授权独立二次签署

### 5.2 移动优先

- 90% 功能在小程序/APP/H5 完成
- PC 是辅助
- 关键路径设计为 3 步以内

### 5.3 一物一码贯穿

- 出库 → 对账单 → 资金大盘 → 数据中台 全链路携带 sku_id + bundle_code

### 5.4 不要做的（与战略红线一致）

- ❌ 资源圈公开池（避免找钢网陷阱）
- ❌ 多家比价（默认 AI 单一报价）
- ❌ 平台直接放贷
- ❌ 自营贸易
- ❌ 客户找钢贸商反向通道（保护卖家私产）

### 5.5 必须做的

- ✅ 钩子设计（信息钩 + 利益钩 + 网络钩）
- ✅ 5 个替代场景（替代微信群/电话/磅单/银行APP/纸质合同）
- ✅ 30 天习惯养成机制
- ✅ 客户主权 6 个月
- ✅ 数据合规与脱敏

## 八、风险与应对（架构层）

| 风险 | 应对 |
|---|---|
| 数据中台延期影响 SaaS | 数据中台与 SaaS 解耦，SaaS 可先用 mock 数据 |
| 主数据建模不准 | M3 末发起一次主数据 review，不对就重构 |

| 集成第三方失败（钢联/磅秤/支付） | 多源备份 + 降级策略 |
